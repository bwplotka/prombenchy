# verify-metrics

`verify-metrics` is a verification tool that ensures all Prometheus metric names generated by [Avalanche](https://github.com/prometheus-community/avalanche) for a scenario are ingested and queryable.

It supports verifying metrics via:
1. **PromQL** (`-mode=promql`): Queries Google Managed Prometheus PromQL API or a local/remote Prometheus instance (`/api/v1/query`).
2. **GCM TimeSeries** (`-mode=gcm`): Queries Google Cloud Monitoring v3 `timeSeries.list` API.
3. **Both** (`-mode=both`): Verifies across both backends.

Expected metrics are determined either:
- Automatically from the running Kubernetes deployment (`kubectl get deployment avalanche -n <namespace>`)
- From an Avalanche YAML manifest (e.g. `./manifests/load/avalanche.exampletarget.yaml`)
- Via explicit CLI flags (e.g. `-gauge-metric-count=158`, `-counter-metric-count=280`, etc.)

## Usage

### Direct Go Execution

```bash
# Verify against running scenario 'gmp' in cluster 'bwplotka-rw' via PromQL
go run ./tools/verify-metrics/main.go -bench-name=gmp -cluster-name=bwplotka-rw -mode=promql

# Verify via GCM timeSeries API
go run ./tools/verify-metrics/main.go -bench-name=gmp -cluster-name=bwplotka-rw -mode=gcm

# Verify via custom local Prometheus endpoint
go run ./tools/verify-metrics/main.go -bench-name=gmp -promql-url=http://localhost:19090/api/v1/query

# Verify against staging endpoint (staging-monitoring.sandbox.googleapis.com)
go run ./tools/verify-metrics/main.go -bench-name=prom-rw -scenario=./manifests/scenarios/prom-rw -staging=true

# Output structured JSON
go run ./tools/verify-metrics/main.go -bench-name=gmp -cluster-name=bwplotka-rw -format=json
```

### Staging Verification

For scenarios that write to Google Cloud Monitoring sandbox/staging (e.g. `staging-monitoring.sandbox.googleapis.com`):
- Pass `-staging=true` (or `STAGING=true` via Makefile)
- Staging is also **automatically detected** if `-scenario` points to a directory containing manifests referencing `staging-monitoring` or `sandbox.googleapis.com`.
- Automatically attaches `X-Goog-User-Project` header for quota validation.

```bash
# Via Makefile
make verify BENCH_NAME=prom-rw SCENARIO=./manifests/scenarios/prom-rw CLUSTER_NAME=bwplotka-rw STAGING=true

# Via shell script
bash ./scripts/bench-verify.sh prom-rw ./manifests/scenarios/prom-rw bwplotka-rw promql true
```

### Options

| Flag | Description | Default |
|------|-------------|---------|
| `-bench-name` | Benchmark name (and k8s namespace) | `""` |
| `-cluster-name` | GKE cluster name filter | `""` |
| `-project-id` | GCP project ID | Current gcloud project |
| `-mode` | Query mode: `promql`, `gcm`, or `both` | `promql` |
| `-staging` | Use staging GCM endpoint (`staging-monitoring.sandbox.googleapis.com`) | Auto-detected from scenario, or `false` |
| `-promql-url` | PromQL query endpoint | GMP PromQL API URL (prod or staging) |
| `-token` | Bearer token for API | Auto-acquired via gcloud auth |
| `-load-manifest` | Path to avalanche manifest | `./manifests/load/avalanche.exampletarget.yaml` |
| `-format` | Output format (`table` or `json`) | `table` |
| `-concurrency` | Concurrent worker count. Higher values risk HTTP 429 quota errors | `4` |
| `-batch-size` | Metrics per batched PromQL query | `25` |
| `-max-retries` | Retries for throttled/transient failures (HTTP 429, 5xx) with exponential backoff | `5` |
| `-timeout` | Overall verification timeout | `300s` |
| `-lookback` | Lookback interval for GCM time series query | `15m` |

### Result classification

Every metric lands in exactly one of three buckets, and the distinction matters:

| Bucket | Meaning |
|--------|---------|
| `QUERYABLE` | The backend returned data for the metric. |
| `MISSING` | The backend answered successfully but had **no data**. This is a genuine gap. |
| `ERRORED` | The query itself failed (quota exhaustion, timeout, backend error). The metric's state is **unknown** — this is *not* evidence of missing data. |

A run with any `ERRORED` metrics is reported as `INCONCLUSIVE` rather than `FAILED`, and the
error messages are printed grouped by kind. If you see HTTP 429 (`Resource has been exhausted`),
lower `-concurrency` or raise `-max-retries`; the read quota on the Managed Prometheus /
Cloud Monitoring APIs is easy to trip, and treating those errors as missing data produces
large phantom gaps that change from run to run.

### Exit codes

| Code | Meaning |
|------|---------|
| `0` | All expected metrics are queryable. |
| `1` | At least one metric is genuinely missing. |
| `2` | Verification was inconclusive (queries failed; nothing can be concluded). |

### Native histograms

Native histograms are verified as `<name>_count`. The current GCM API does not support querying
native histograms as such: an ingested native histogram is a distribution, which the GMP PromQL API
exposes only as `_count` / `_sum` / `_bucket`, so querying the bare family name always returns empty.

### Authentication

`verify-metrics` automatically uses `gcloud` to authenticate against Google Cloud Monitoring / Managed Prometheus endpoints:
- Automatically runs `gcloud auth print-access-token` using the active gcloud account.
- Falls back to `gcloud auth application-default print-access-token` if needed.
- Accepts explicit token via `-token=<token>` or `BEARER_TOKEN` environment variable.
- Adds `X-Goog-User-Project` header automatically for quota management.
